# ADR 0015 — Airlock pipeline architecture (M4-T2 / T3 / T4)

**Status:** Accepted · **Date:** 2026-09-04 · **Refs:** ARCHITECTURE §21.3, §21.4, §21.5, §25; ROADMAP M4-T2/T3/T4; ADR-0007 (podman lifecycle), ADR-0010 (M2 security suite)

## Context

M4 (Airlock & Gateway) is the milestone that unlocks real file and network capability for the agent — but only through scanning and allowlisting. The M4-T1 path-containment library (`internal/airlock/paths`, shipped in `5f829b7`) is the *structural* half of that: every file operation routes through `paths.Resolve` / `paths.Validate` / `paths.OpenNoFollow` so the kernel never sees a syscall the library has not vetted.

M4-T2, T3, and T4 are the *behavioral* half: who decides what gets through, on what evidence, and what to do with the bytes that don't. The architecture is broader than the file airlock (it also covers the eventual network gateway, T5–T7), so a single ADR is the right place to lock in the *shape* of the scanning layer before the implementations land.

Three questions were open as of the M4-T1 close-out:

1. **Where do scanners live?** The Gate G1 contract (`internal/gate/gate_test.go`) forbids `os/exec` everywhere in `internal/` and limits it in `cmd/` to one named file (`cmd/athanor/jobpod_client.go`). M2-T6 already shipped the security suite through that exception. ClamAV and YARA are external binaries; their adapters need `os/exec`. The Gate G1 boundary must be extended deliberately, not silently.
2. **What is the Scanner interface?** A scanner that takes a filesystem path and returns a verdict looks tidy but leaks the implementation (every scanner that wants to scan a stream has to write to a temp file). A scanner that takes a `ScanInput` with both `[]byte` and an `io.Reader` is more honest about the underlying work.
3. **Which scanners run where?** A single global scanner set would scan everything with everything, which is wrong on three counts: egress data was generated by the LLM (prompt-injection scanning is a category error), user-typed goals are operator-as-principal (the heuristic is a courtesy, not a gate), and the *high-leverage* scanner for internet content is the security-persona classifier that lives behind the gateway (T5), not in the airlock.

## Decision

### 1. Scanner interface — pure, streaming-aware, explicit verdict

The `Scanner` interface lives in `internal/airlock/scanner/scanner.go`:

```go
type Verdict int
const (
    VerdictClean Verdict = iota
    VerdictUncertain       // quarantine-on-uncertainty
    VerdictRejected        // hard rejection
)
type ScanInput struct {
    Path  string
    Bytes []byte      // nil if the scanner should read from Reader
    Reader io.Reader   // for streaming scanners (clamdscan, yara); Bytes takes precedence if non-nil
    Size  int64
    Mode  os.FileMode  // post-Validate, pre-copy
}
type ScanResult struct {
    Verdict  Verdict
    Reason   string         // stable, machine-readable; e.g. "scanner:clamav:Win.Test.EICAR_HDB-1"
    Details  map[string]any // scanner-specific; JSON-encoded into the quarantine row
    Duration time.Duration
}
type Scanner interface {
    Name() string
    Scan(ctx context.Context, in ScanInput) (ScanResult, error)
}
```

Three properties this gives us:

- **Pure functional core, impure edges.** A scanner is a function `(ctx, in) (result, err)`. The binary adapters that shell out to clamd / yara are the impure edge; everything else (the registry, the pipelines, the audit-row shapes) is testable with a fake scanner.
- **Worst-wins aggregation.** A registry's `RunAll` returns the most severe verdict across all scanners (`Rejected > Uncertain > Clean`). A single `Uncertain` from the prompt-injection heuristic is enough to quarantine; a single `Rejected` from ClamAV is enough to reject. There is no "averaging" of verdicts.
- **Failure mode is fail-closed.** A scanner that returns a non-nil `error` is treated as `VerdictUncertain` with reason `scanner:<name>:error:<err>` and the file is quarantined. The pipeline never silently passes on scanner failure.

### 2. Trust boundaries, not all text

The architecture scans at *every* trust crossing. But the scanner quality is asymmetric, allocated by leverage:

| Crossing | Choke point | Primary scanner (high leverage) | Secondary scans (cheap, layered) |
|---|---|---|---|
| Internet byte → context content | Gateway (T5) | `prompt-injection-classifier` (security persona, Temp 0.0) | size, zipbomb on fetch response |
| Inbox file → workspace `.processed/` | Ingress watcher (T2/T3) | `prompt-injection-heuristic` | size, zipbomb, clamav, yara |
| User prompt (long) → first-class instruction | `api.goal.submit` | `prompt-injection-heuristic` (long-prompt only, >2 KiB) | none |
| Skill manifest → mounted prompt template | Skill install path | heuristic + YARA baseline | (out of scope M4 per ADR-0016) |

**Egress is its own concern.** Egress data was generated by the LLM; prompt-injection scanning egress bytes is checking for a thing that cannot happen. Egress runs `size + zipbomb + clamav + yara` only — no prompt-injection scanner at egress, ever. Documented in code as a `PipelineEgress` selection that omits `prompt-injection-*` names.

The principle is *defense in depth at every crossing; asymmetric effort by leverage*. The narrowest choke point gets the highest-quality scanner; other checkpoints get cheaper, lower-quality scanners tuned to be cheap-false-positive.

### 3. Pluggable registry, parameterized by pipeline

The `Registry` is queried by name and parameterized by `PipelineKind`:

```go
type PipelineKind string
const (
    PipelineIngress    PipelineKind = "ingress"
    PipelineEgress     PipelineKind = "egress"
    PipelineUserPrompt PipelineKind = "user-prompt"
)
```

The config declares three lists — `airlock.scanners.ingress`, `airlock.scanners.egress`, `airlock.scanners.user_prompt` — and `NewRegistry` instantiates the named scanners. **Absent in-tree scanner name → error at construction** (typos caught at config-load). **Absent external scanner** (clamav binary not installed) → log + register a stub that returns `VerdictUncertain` with reason `scanner:<name>:absent` so the pipeline fails closed. This is the same fail-closed posture as M2-T6: missing capability is logged and degrades to quarantine, never to silent pass.

### 4. External scanners in `cmd/athanor/scanners/`

ClamAV (`clamdscan`, fallback `clamscan`) and YARA (`yara`) adapters live in `cmd/athanor/scanners/`. This extends the Gate G1 `os/exec` allowlist from a single named file to a package of three files (`scanners.go`, `clamav.go`, `yara.go`). The extension is a **deliberate Gate G1 amendment** recorded in `internal/gate/gate_test.go` — the test's doc comment is updated to record the new exception, the AST walk continues to forbid `os/exec` everywhere else, and the amendment lands in the same commit as the first scanner commit (M4-T3) so it is reviewable as a single diff.

The binary adapters use `os/exec.CommandContext` so a hung subprocess cannot wedge the daemon. Default timeout 30 s, configurable.

### 5. Idempotency by content hash

The ingress processor computes SHA-256 of the file bytes before any scanning. Re-ingesting the same content finds the `quarantined_files` row by primary key, or finds the `.processed/<sha256>.*` marker, and drops the event with an audit `duplicate_ignored` row. This makes the pipeline safe to run concurrently and safe to re-trigger on retry.

The user-typed goal's long-prompt heuristic operates on a string, not a file, so idempotency there is per-submit, not content-hash-based.

### 6. Originals untouched

The ingress pipeline never `os.Remove`, `os.Rename`, or `os.Chmod`s the user's file at `workspace/inbox/<name>`. All writes go to `.processed/<sha256>.<ext>` (clean) or `quarantine/<YYYY-MM-DD>/<sha256>.<ext>` (rejected/uncertain). The user's file stays where they put it; the audit log explains what the pipeline did with it. This is the strongest AC in ROADMAP M4-T2 and the only one that protects the user from losing data they deliberately placed in the inbox.

Path-layer rejections (`ErrAbsolute`, `ErrTraversal`, `ErrInvalid`) are not quarantined — the user wrote a path that the airlock refuses to touch. The file remains in place; an `airlock` audit row records `event: "rejected"` with the path error. Operators who drop files with weird paths can see what happened without the pipeline hiding their input from them.

### 7. Egress is a subscriber, not an engine hook

The egress loop subscribes to the event log for `category=artifact, event=accepted` rows and runs asynchronously. The engine is unchanged — it does not know the airlock exists. This preserves the M3 engine's tested surface and keeps the airlock as an *observer + executor* rather than a *driver*. M3-T6's crash-recovery E2E suite keeps passing without modification.

The same `internal/v1/exports/<id>` API also serves the manual `athanor export` CLI subcommand, which calls the same exporter synchronously and returns the result.

## Consequences

- **Gate G1 amendable in one place.** The new allowlist entry for `cmd/athanor/scanners/*.go` is the only structural change. Future external scanners (a ClamAV REST adapter, a VirusTotal client) extend the same package; future scanners that need a different impure edge (e.g. a Python-based heuristic that requires `os/exec`) need a new allowlist entry, which is the right friction.
- **One `Scanner` interface, three pipeline selections.** The interface is a one-page contract. The pipeline selections are config-driven and reviewable in `config.example.yaml`. A future operator who wants the heuristic disabled at ingress sets `airlock.scanners.ingress: [size, zipbomb, clamav, yara]` and the registry honors it.
- **Egress data is never prompt-injection-scanned.** The asymmetry is documented in the registry's `RunAll` and pinned by a unit test (`TestRegistry_EgressOmitsPromptInjection`). Future contributors cannot accidentally re-enable it without changing a test.
- **Long-prompt heuristic on goal submit is opt-out.** The 2 KiB threshold is a heuristic, not a security boundary. A determined operator can disable it (`airlock.prompt_injection_scan_long_user_prompts: false`) or paste a 1.9 KiB payload to bypass it. The defense is *layered* — the gateway (T5) is the high-leverage one, this is a cheap obvious-case filter.
- **The airlock has no knowledge of the LLM.** It scans bytes; it does not interpret them. The pipeline that feeds bytes into the LLM (M3 engine, T5 gateway) is the thing that handles LLM-specific concerns (context feasibility, prompt assembly). This separation keeps each component small and testable.

## Not in M4-T2/T3/T4

- **T5–T7** (gateway, reader mode, gateway-backed tools) — the gateway is where the *high-leverage* prompt-injection scanner (`prompt-injection-classifier`, security persona, Temp 0.0) lives. That lands in T5.
- **T8** (adversarial security suite: traversal payloads, zip bombs, injection corpus, SSRF attempts) — the test corpus for the in-tree scanners lands *inside* T3, but the formal Gate G4 close-out suite is a separate task.
- **Quarantine total-bytes cap.** No size cap on the quarantine directory in M4. A follow-up T8 task should add `quarantine_total_bytes_cap` and a sweep-oldest eviction policy.
- **Egress artifact size cap.** Same as above.
- **Skill-manifest scanning.** Out of scope per ADR-0016 (third-party skills are explicitly discouraged).
- **Cross-pipeline correlation.** The quarantine rows are independent per pipeline. A future M5 or M6 task could correlate a quarantined egress export back to the artifact that triggered it, but M4 does not need that.

## Forward references

- M4-T5 (Gateway) implements the `prompt-injection-classifier` scanner that the table above names. The T5 scanner slots into the registry as another `Scanner` impl, dispatched only from gateway-mediated code paths.
- M4-T8 (Adversarial security suite) draws the rejection corpus from the table-driven tests in `internal/airlock/scanner/scanner_test.go` and the ingest pipeline in `internal/airlock/ingress/ingress_test.go`.
- M5 (Context Engine) will add a *different* trust crossing: dormant chunks swapped back into active context. The scanner that runs on swap is a future ADR; the Scanner interface in this ADR is shaped to accommodate it.
